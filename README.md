# claude-code-harness-antigravity-sdk

Claude Code as the **driver**, Gemini 3.5 Flash via the **Google Antigravity
SDK** as the **worker**, run end-to-end against two workloads:

| Kind | What it is | Entry point |
|---|---|---|
| **SWE-bench Pro** | resolve real GitHub issues in sealed containers, graded by Scale's evaluator | `kinds/swepro.mjs` |
| **SDLC** | build a greenfield service from a brief, graded on build + full test suite | `kinds/sdlc.mjs` |

Extracted from Tilicho's studies monorepo. The harness source is byte-identical
to the code that produced the evidence in `runs/` — see *Differences from the
source repo* at the bottom for the four exceptions, none of which is code.

## The claim this repo lets you check

Two different things are claimed, and they are not equally strong. The
distinction is the point of the whole apparatus:

- **Provenance** — every delivered byte was authored by the Gemini worker
  process. This is **mechanically enforced**: the driver runs with its
  file-editing tools removed, and a PreToolUse hook rejects any shell command
  that would write into the repository tree. Measured at **100%**.
- **Attribution** — Gemini did the *engineering thinking*. This is **not**
  enforceable, and we do not claim it is. The hand-off channel is free text, and
  free text can carry a finished function. So every hand-off is committed and
  linted, and the findings are published including the bad ones.

`fixtures/delegation-corpus/` holds 50 real hand-offs, hand-labelled 44 clean /
6 solution-leaked, with the exact lint verdict each produced when the thresholds
were pinned. `pnpm test` replays the lint over all of them.

|---|---|

| Docker | every graded run executes in a container; ~5 GB free |
| Claude Code CLI | the driver runtime, logged in |
| gcloud ADC | `gcloud auth application-default login` — the worker reaches Gemini through Vertex |
| Python 3.11+ | `gemini_worker.py`; see `tools/harness-matrix/sdk-probe/README.md` for the venv |

## Run it

```sh
pnpm install
pnpm build
pnpm test          # offline, no credentials, no spend
```

`pnpm dry-run` prints the exact opening frame a paid run emits, executing
nothing and spending nothing. Read that before paying for a column.

## What is in `runs/`

134 files of delegation evidence across the ten delegated runs on
record: for each hand-off, `worker-task-<phase>-a<N>-<M>.md` is the verbatim
text the driver sent, and `worker-usage-<phase>-a<N>-<M>.json` is the SDK's own
receipt — model, SDK version, Vertex project and location, token counts.

The bulk of a run (the repository checkout, trajectories, graded diffs — 880 MB)
is not published. `tools/harness-matrix/.gitignore` documents exactly what is
kept and why.

## Differences from the source repo

Four, all mechanical, none in the harness source:

1. **Host paths are scrubbed.** The evidence was written by processes on a
   laptop and carried its absolute paths. `scrub-paths.mjs` rewrites them to
   `/harness`, `/repo` and `/home/user`. The substitution is gated: each
   hand-off is linted before and after, and extraction aborts if any warning
   family moves — so the findings here cannot disagree with the ones published
   on the dashboard.
2. **Three package manifests are regenerated minimal.** The originals declare
   workspace siblings and build scripts for source this repo does not ship;
   `pnpm install` would fail on them. Dependency versions are copied exactly.
3. **`packages/swe-bench/tsconfig.json` is narrowed** to the two files the
   harness imports. The other files in that package `import type` from a
   package not shipped here.
4. **Root `package.json`, `pnpm-workspace.yaml`, `.gitignore` and this
   README are generated.** The monorepo's own root files describe apps that do
   not exist here.

Generated by `extract-repo.mjs`, which lives in the source repo alongside the
harness. Re-running it reproduces this tree.
